# MS5 — Rework: dependency-aware patches, then Copilot

Sub-plan of [PLAN.md](PLAN.md); working rules there apply. Requirements: [spec.md](spec.md) (Migration level 3, Build and verify, guiding principle "save tokens").

For items whose diff does not apply (`conflicts`) or whose patch does not build, make a patch that does: first without Copilot (stack the prerequisites, merge with a base found in the source tree), then with Copilot on only what is still failing. Results are `migration_patch` rows that go through the MS6 build. Comes before MS2-2: it needs the Copilot adapter, not the MS2-2 verdicts.

## Decisions

- **Ladder (cheapest first, per diff file):** each rung only runs for the files the rung before left failing.
  1. *Stack:* apply on HEAD plus the prerequisites' patches (plain, then 3-way). No Copilot.
  2. *Source base:* for a preimage blob the target lacks (`missing`), add the source project's object store as an alternate and 3-way merge again. No Copilot. Source project = same path in the source tree; not there, or no such blob: skip the rung (manual mapping later).
  3. *Resolve (3a):* Copilot resolves the conflict markers a real 3-way left in the files.
  4. *Port (3b):* Copilot ports the `.rej` hunks of `git apply --reject` (no base for a 3-way) into the current files.
  5. *Re-implement (3c):* Copilot re-implements the file's change from intent (file moved, rewritten or gone). Only on explicit request.
  Rungs 1–2 make a patch with level `stacked` / `source3way`; 3–5 make one with source `ai` and level `resolve` / `port` / `reimpl`.
- **Dependencies:** prerequisites are the items making the `pending` blobs of the item's `diff_dependency` rows, followed transitively; plus the cluster members before it when the item is in a cluster (cluster order). Ordered topologically (ties: cluster order, then key). A cycle, or a set the user selects as one unit, is reworked together: one scratch checkout, one Copilot session.
- **Prerequisites outside the selection:** the Rework dialog lists them and adds them by default. Closed / not relevant ones are listed with a warning and left out unless ticked; a left-out prerequisite with an accepted patch is still used as base, one without is not (the item is reworked without it, noted in the attempt).
- **Base of a patch:** HEAD plus the patches below it. `migration_patch` gains `base_patch_ids` (ordered, empty = on HEAD alone). A patch is stale when the HEAD moved, any base patch is no longer its item's current patch, or the item has a newer diff version. A stale accepted patch stays buildable (as a stale MS6 patch does today) until reworked. A prerequisite's patch: its current accepted patch (`original` or `ai`); one still `proposed` may be used as a base, but the dependent's patch cannot be accepted until that base is.
- **Scratch checkout, never written in the user tree:** per project, `git clone --shared --no-checkout` of the target project into `<data>/workspaces/<id>/rework/<attempt>/<project>`, sparse checkout of the files the item's diffs touch at HEAD, base patches applied and committed there (so `git diff <base commit>` is the item's patch alone). Copilot writes only there; for other code it reads the user's target tree read-only (clean at HEAD: rework never runs during a build; it lacks the base patches, which the bundle carries). Deleted after the attempt (kept on failure with setting `rework.keep_scratch`). `--shared` only reads the project's object store; the pre-scan rule "never mutate" holds.
- **Patches come from git, not from the model:** Copilot edits files in the scratch checkout; the patch is `git diff --binary -M <base commit>` there. Copilot never writes a diff.
- **Copilot adapter:** standalone `copilot` CLI behind an interface (`CopilotClient`), as in the first MS2 plan (`ms2` commit `40cd8a2`, not in this clone: rewritten). Run with the scratch checkout as cwd, non-interactive, file writes only inside it, the target tree readable, shell and network denied. Exact flags from the 5.2 spike (below). **Fallback** when the CLI cannot be limited that way: prompt-only, tools off; Copilot answers with search/replace blocks per file that we apply in the scratch checkout (a block that does not match exactly fails the round). Settings: binary path, model per rung (cheap for 3a, stronger for 3b/3c), caps, build-fix rounds, a "Test Copilot" button. A fake CLI (canned edits) for tests.
- **Budget:** hard caps on Copilot calls: per item (default 5, across rungs, fix rounds and intent retries; reached: the item fails with "Copilot budget reached") and per job (default 100; reached: the remaining items get only rungs 1–2). Both settings, changeable in the dialog. The dialog shows an estimate; attempts store calls and any usage the CLI reports.
- **Context bundle (per Copilot call, fixed priority, cut at the cap):** ticket summary and description (trimmed); the user's reject note and the previous attempt's failure reason, if any; the failing files only: conflict regions with N lines around, or `.rej` hunks plus the current code where they would go; the original diff's sections for those files; for each prerequisite touching the same files, its original diff against its migrated patch for those files (shows renames and API changes the dependent needs too) and its summary; for 3c, the source tree's before/after of the file. Stored with the attempt. Asked to end with a short explanation per file (shown in review).
- **Checks before the build (no Copilot):**
  - Mechanical: no conflict markers or `.rej` files left; the patch `git apply --check`s on its base; touches only the item's files (others flagged).
  - Intent (`rework/intent.py`), against the original diff per file: added lines kept (normalized whitespace), identifiers and string literals the original adds also added, no original hunk dropped, no removal the original did not make. Thresholds per rung: strict for resolve, looser for port, warning only for re-implement.
  - A failure is fed back as a fix round ("hunk 3 of foo.c missing"). Mechanical failures that remain fail the attempt; intent findings that remain after the rounds leave the patch `proposed` with the findings shown in review.
- **Build (MS6, extended for every patch source):** a patch that touches a header, an `Android.bp` / `.mk` export or a public API also builds the modules depending on the changed ones (reverse dependencies from `module-info.json`, capped, setting `build.dependents_cap`) and, for a Java public API (`api/*.txt` or an `@SystemApi`/public class change), the matching API check target. Applies to `original` and `3way` patches too.
- **Build-fix loop:** a rework attempt builds its patch (MS6 runner, stacked on its base) and feeds the build error summary back to Copilot for up to `rework.build_rounds` rounds (default 2), stopping early when a round changes nothing or the errors repeat. A build error naming a symbol that another item's diff adds is reported as a likely missing dependency instead of another round.
- **Review gate:** `ai`, `stacked` and `source3way` patches are `proposed`; the user accepts or rejects the whole patch (`migration_patch.review`: `proposed` / `accepted` / `rejected`; `original` patches are `accepted`). A reject takes an optional note, used in the next rework's bundle. Accept only makes the patch buildable; MS7 human review stays a separate step for every item. Build eligibility (MS6): triage `applies` / `3way`, or an accepted current patch.
- **Failed rework:** an item ends `rework_failed` with the reason (e.g. "hunk 2 of AudioPolicy.cpp: target file rewritten"). The next rework of it starts from the failure: the reason and note go into the bundle, and the dialog preselects the next rung (e.g. re-implement).
- **Ripple:** accepting a new patch for a prerequisite makes its dependents' patches stale ("base <key> changed"). Nothing reworked automatically: the user reworks them, with "include dependents".
- **Trigger and UI:** user-started only. One "Rework…" dialog, opened from the backlog bulk toolbar and from the item's Migration tab (item preselected): order (as in `StackedDialog`), missing prerequisites, rungs (3c off by default, next rung preselected after a failure), "include dependents", caps, estimate. Build and pre-scan job results with conflicts or `ai` build failures offer "Rework these?", which opens the dialog with them preselected; never started automatically. A merged "Migrate…" dialog for build and rework is decided after MS5.
- **Job:** `rework_job` like `build_job` (one per workspace, progress, cancel, one failing item does not stop the job). Refused while a build or pre-scan runs in the workspace, and the other way round. Cancel kills the Copilot process and deletes the scratch.
- **Not now:** tests after the patch (MS6-2), semantic dependencies beyond blobs and clusters (MS2-2), Copilot review of a patch against the original (opt-in, later), editing a proposed patch by hand (`manual` source, later), manual target→source project mapping, Copilot via API instead of CLI.

## Data model (additions, sketch)

- `migration_patch` — `base_patch_ids` (JSON, default `[]`), `review` (`proposed` / `accepted` / `rejected`), `review_note`, `attempt_id` (nullable), `findings` (JSON: intent and check findings); `source` adds `ai`, `level` adds `stacked` / `source3way` / `resolve` / `port` / `reimpl`
- `rework_job` — like `build_job` (workspace_id, issue_keys in order, options: rungs, include dependents, caps; status, done, total, calls, errors, times, cancel_requested)
- `rework_attempt` — id, job_id, item_ids (JSON, several for a unit), project HEADs, base_patch_ids, rungs tried, per file outcome (rung that fixed it or why it failed), Copilot calls (model, prompt bundle path, response, explanation, usage if reported, duration), build rounds (run ids), status (`patched` / `failed` / `canceled` / `error`), reason, started_at, finished_at
- `item` — `rework_status` (`proposed` / `accepted` / `rework_failed`), `rework_reason`, `reworked_at` (backlog column, count bar and filter, like build)

## Steps

**5.1 Patches on a base** — done
- Migration adds `base_patch_ids`, `review`, `review_note`, `findings` (existing rows `accepted`). `prescan/chain.py`: prerequisites of an item from `diff_dependency` (+ cluster order), topological order, cycles as units. Stale check extended by base patches. Stacked build switches from restacking the original diffs to the members' current patches (falling back to the diff when it has none, as today).
- Test: chain from fixture dependencies (PROJ series with `pending` rows), cycle detection, order ties, stale on base change, stale accepted patch still buildable, stacked build of patches with a base.
- Done as: migration `0018`, `findings` a JSON list (default `[]`). `prescan/chain.py`: `item_needs` (current diffs' `pending` rows plus the previous cluster member), `chain(session, workspace, item_ids)` gives `units` (Tarjan cycles, then topological with a heap on the tie key `(not in a cluster, position, key)`; inside a unit the same key), `needs` and `keys`. A rework patch is one with a level in `REWORK_LEVELS`; `patch_plan` replaces, per project, the originals of the item's current diffs with its newest rework patch that is not rejected (a diff with neither stays the diff), `current_patches` the patches of it. `patch_stale`: `<project> HEAD moved` against `base_head`, `base <key> changed`, `base patch gone`, `new diff version` (a current diff whose Jira `created` is after the patch). `chain.stale_items` is the scan staleness plus that for items with rework patches; the APIs use it. Build: an item with a rework patch is buildable when every current rework patch is accepted (skipped as `patch proposed: <project>` otherwise), is never re-scanned, and goes in after its base patches (in `patch_ids`, once each) with `base_head` None (`tree.prepare` checks no HEAD then) and `--3way`. Stacked build stacks each item's `patch_plan` (`patch <id> (<project>)` in the log). Patch list API returns `base_patch_ids`, `review`, `review_note`, `findings`, `current` from `current_patches`; the Migration tab names the new levels.

**5.2 Copilot adapter spike and client** — done
- Spike: run the installed `copilot` CLI in a scratch git checkout: non-interactive flags, writes limited to the cwd with another directory readable, shell denied, model choice, whether usage is reported. Write the findings here and pick tool mode or prompt-only fallback.
- `copilot/client.py` (`CopilotClient.run(cwd, prompt, model, timeout, read_dirs) -> CopilotResult`), the search/replace block applier for the fallback, settings (binary, models per rung, caps, rounds), `POST /settings/copilot/test`, settings form. Fake CLI in `tests/fake_copilot/` (canned file edits or blocks by prompt marker).
- Test: client against the fake (success, timeout, non-zero exit, cancel kills it), block applier (exact match, no match fails, several blocks per file), settings validation.
- Spike findings (`@github/copilot` 1.0.105, the standalone CLI). Not logged in here, so it ran in its offline BYOK mode (`COPILOT_OFFLINE=true`, `COPILOT_PROVIDER_BASE_URL`) against a local fake OpenAI endpoint that logged each request and replayed scripted tool calls; the permission checks are the CLI's own, the same as with Copilot's models.
  - Non-interactive: the prompt on stdin (no `-p`, which would hit the 128 KB argv limit; 300 KB came through whole), `-s` prints only the final answer, exit code 0 / 1 (1 also when the model endpoint is unreachable). `--no-auto-update`, `--no-custom-instructions` (AOSP trees may carry `AGENTS.md`), `--no-ask-user`, `--disable-builtin-mcps`.
  - Tools: by default `bash`, `view`, `create`, `edit`, `grep`, `glob`, `task`, `sql`, workflow and agent tools and more. `--available-tools view create edit grep glob` leaves only those (a call to `bash` gets "Tool 'bash' does not exist"). The list is variadic: the next argument must be an option.
  - Paths: access is limited to the cwd, the temp dir and each `--add-dir`; anything else needs approval, which in prompt mode is refused. `--disallow-temp-dir` drops the temp dir. `--add-dir` grants writes too, and `--deny-tool 'write(<dir>)'` does not stop them; `write(<dir>/*)` stops only direct children; `write(<dir>/**)` stops every write below it, also through a symlink in the cwd (paths are resolved). So: `--allow-tool write` plus `--deny-tool 'write(<read dir>/**)'` per read dir and `write(<cwd>/.git/**)` (no hooks or alternates planted in the scratch clone).
  - Model: `--model <id>` (or `COPILOT_MODEL`); unset uses the CLI's default (`auto` lets Copilot pick).
  - Usage: `--usage-output-file <file>` writes JSON: `totalPremiumRequestCost`, `totalUserRequests`, `totalNanoAiu` / `aiCreditsStatus` (AI credits where billed that way), and per model `requests.count` (model API calls, one per tool round) and input / output / cache tokens. Also written when the call fails. `--max-ai-credits` exists for a per-session cap, not used yet.
  - Decision: tool mode. The prompt-only fallback (search/replace blocks) is kept for a CLI that cannot be limited this way.
- Done as: `copilot/client.py`: `command(...)` builds the flags above; `CopilotClient(binary, env, kill_grace).run(cwd, prompt, model, timeout, read_dirs, cancel, tools)` with stdin from a file, stdout / stderr to files, own process group, SIGTERM then SIGKILL on timeout or cancel, gives `CopilotResult` (`ok` / `failed` / `timeout` / `canceled`, answer, exit code, stderr tail, usage JSON, duration); `version()`. `copilot/blocks.py`: `parse_blocks` (path line, optional code fence, `<<<<<<< SEARCH` / `=======` / `>>>>>>> REPLACE`), `apply_blocks` (in order, each SEARCH exactly once, empty SEARCH creates a missing file, all or nothing, no paths outside the checkout, through a symlink or into `.git`). Settings in `config.toml` sections `copilot` (`binary`, default `copilot`; `model_resolve` / `model_port` / `model_reimpl`, unset: CLI default; `timeout`, 900 s) and `rework` (`item_cap` 5, `job_cap` 100, `build_rounds` 2), env overrides `AOSP_MIGRATOR_COPILOT_*` / `AOSP_MIGRATOR_REWORK_*`, `Config.copilot()`; a stored number out of range falls back to the default. `PUT /settings` takes `copilot` / `rework` (empty or 0 restores the default, -1 for build rounds), `POST /settings/copilot/test` (unsaved `binary` / `model`; `--version`, then one short prompt with only `view` in an empty temp dir). Settings page: Copilot form with "Test Copilot". Fake CLI `tests/fake_copilot/copilot`: scenario by `@@fake:<name>@@` in the prompt (`scenarios/*.json`: reply, edits, creates, sleep, exit, stderr), refuses writes like the real one, writes a usage file, logs calls to `FAKE_COPILOT_LOG`.

**5.3 Build of dependents and API checks (MS6 extension)** — done
- `build/modules.py`: reverse dependencies from `module-info.json` (`dependencies` / `shared_libs` / `static_libs` fields as present) for modules whose header, export or API file changed, capped; API check target for Java API changes. Used by every build unit.
- Test: synthetic `module-info.json` with a header change pulling in its users, the cap, a `.c` change pulling in nothing extra, an `api/current.txt` change adding the check target; fake envsetup logs the wider target list.
- Done as: `modules.widening_files(project, changes)` gives the changed files that reach other modules (header `.h` / `.hh` / `.hpp` / `.hxx` / `.inl`, `Android.bp` / `.mk`, `.aidl`, a `.java` whose added or removed lines declare something `public` / `protected` or carry `@SystemApi` / `@TestApi`) and the API ones (that Java, `api/*.txt`). `read_module_info` returns `ModuleInfo` (`by_path`, `users`: module name to the modules naming it in `dependencies` / `shared_libs` / `static_libs` / `libs`, whichever are present, arch variants by `module_name`). `affected_modules(changed, tree, root, reaching, api, dependents_cap)`: the direct users of the modules of reaching files, minus the changed modules, sorted, the first `dependents_cap` (`dependents`, `dependents_left_out`), then `checkapi` for any API file (`api_check`); `targets` is changed modules, dependents, check target. Only with `module-info.json` (`m`); with `mmm` the log says they were not built. The build runner passes them for every unit (all patch sources) and logs the dependents and the API files. Setting `build.dependents_cap` (default 20, 0 for none, env `AOSP_MIGRATOR_BUILD_DEPENDENTS_CAP`), `PUT /settings` `build` (-1 restores the default), "Build" form in Settings.

**5.4 Scratch checkout and rungs 1–2** — done
- `rework/scratch.py`: shared clone, sparse checkout of the touched files at HEAD, base patches committed, real `git apply --3way` (leaves markers) / `--reject`, result per file (`applied`, `merged`, `conflict` with marker regions, `rejected` with `.rej` hunks), patch from `git diff`. Source base: same-path source project's objects as alternate, 3-way again. Cleanup.
- Test: user tree and object store unchanged; only touched files checked out; a fixture item that only conflicts without its prerequisite gets a `stacked` patch; a `missing` blob in a fixture source tree gets a `source3way` patch; a source project at another path is skipped; conflict regions and `.rej` hunks read back correctly.
- Done as: `rework/scratch.py`. `Scratch.create(path, project_dir, files, base_patches)`: `git init --template=` (no user hooks) with the project's object store as the only alternate instead of `clone --shared` (same objects, no copy of the project's refs), local config fixed (identity, no gpg sign, `gc.auto` 0, `merge.conflictStyle` diff3, `core.hooksPath` to the empty `.git/hooks`), non-cone sparse patterns (`sparse_pattern`, literal paths from the top) of `touched_files` (both sides of a rename), detached checkout of the project HEAD; base patches `git apply --cached` (else `--3way --cached`), committed, `reset --hard` (raises `ScratchError` on no history or a base that does not apply, scratch removed). `rungs(diffs, source_project, present)` per file: binary without data `failed`; `apply --index` `applied`; `--3way` `merged` / `conflict` (`regions`: start, end, ours, base, theirs) / missing blob; for those the source project's objects appended to the alternates (once) and `--3way` again (rung `source`), else a note why skipped (`no source tree`, `no source project at <name>`, no history); what is left `apply --reject`: `rejected` with the `.rej` hunks, or `failed`. All applied / merged: level `stacked`, or `source3way` when rung 2 merged a file, patch `git add -A` then `diff --cached --binary -M <base>`. `remove()`. `Config.rework_dir(workspace, attempt)` for `<data>/workspaces/<id>/rework/<attempt>`; the `rework.keep_scratch` setting comes with the runner (5.6). Tests build their own trees (the PROJ-105/106 fixture applies as is either way).

**5.5 Copilot rungs 3a / 3b, checks** — done
- `rework/bundle.py` (bundle under the cap, prerequisite original-vs-migrated deltas, reject note and previous reason), `rework/checks.py` (mechanical), `rework/intent.py` (thresholds per rung), attempt record, `ai` patch `proposed` with findings. Migration adds `rework_attempt`, item rework fields.
- Test with the fake Copilot: resolve markers, port a `.rej` hunk, markers left → failed round, dropped hunk → intent round then flagged, extra file flagged, bundle cut at the cap keeps priority order, prerequisite delta only for shared files, per-item cap reached.
- Done as: migration `0019`: `rework_attempt` (workspace, `job_id` without a foreign key until `rework_job` exists in 5.6, `item_ids`, `heads`, `base_patch_ids`, `rungs`, `files`, `calls`, `build_run_ids`, status `running` / `patched` / `failed` / `canceled` / `error`, reason, times), `migration_patch.attempt_id`, `item.rework_status` / `rework_reason` / `reworked_at`. `rework/ladder.py`: `run(scratch, diffs, context, copilot, budget, source_project, present, target, cancel)` runs `Scratch.rungs`, then resolve (conflict files) and port (rejected files, `.rej` removed first) with the model of the rung; a `failed` file (binary, gone) fails the attempt before any call ("needs re-implement"). Checks after the calls; their errors go back as fix rounds at the highest rung used, with the change so far, until clean, a round that changes nothing, or the `Budget` (calls, shared by the item's projects) is spent: "Copilot budget reached; <first check error>" fails, intent errors alone leave the patch with them. A Copilot call that fails or times out fails the attempt ("Copilot failed: <first stderr line>"). Result: status, reason, level (`resolve`, or `port` when a port ran), patch, per file outcome (`resolved` / `ported` with the rung), rungs, findings, calls (rung, round, model, status, prompt file, bundle parts kept, answer, error, usage, duration), Copilot's answers. `rework/bundle.py`: instructions per rung (files to edit, nothing else, target tree read-only), then in priority the previous round's findings, ticket (description cut at 4000), last failure and reject note, the failing files (conflict regions or `.rej` hunks with the current code, 10 lines around, numbered; in a fix round the change so far), the original sections for them, prerequisites touching them (original next to migrated, "migrated unchanged" when the changed lines match, "not migrated yet"); cut at 60000 characters (the crossing part cut and marked, the rest left out, noted per part), closing request for one line per file. `rework/checks.py`: `Finding` (kind `check` / `intent`, severity, path, message); `mechanical`: `.rej` files, conflict markers (`<<<<<<<`, `|||||||`, `>>>>>>>`; not a bare `=======`) in the files the patch writes, `git apply --check --cached` on the base commit in a temp index, no change at all (errors), files outside the item's diffs (warning). `rework/intent.py`: per file of the original against the file afterwards (added lines kept, normalized, lines without a letter or digit left out), its new identifiers and string literals, hunks with no trace, removals the original did not make (a line whose identifiers are a subset of a removed line's counts as a variant); thresholds resolve strict, port 0.8 / 0.9 / 0 / 2, reimpl warnings only. `rework/attempt.py`: `start`, `record` (a project's ladder result into the attempt), `save_patch` (source `ai` for resolve / port / reimpl, `original` for stacked / source3way, `proposed`, findings), `finish` (items `proposed` or `rework_failed` with the reason; cancel leaves them), `context` (ticket, `last_failure`, `reject_note` of the newest rework patch when rejected, prerequisites' diffs for the project and their current patches there). `Scratch.patch` adds with `--sparse` (a file Copilot creates outside the sparse patterns). Fake CLI: `rounds` in a scenario, one per call with its marker.

**5.6 Rework job, build-fix loop, API**
- `rework/runner.py` (pattern of `BuildRunner`): order, missing prerequisites, units, rungs per options, include dependents, per-job cap (then rungs 1–2 only), build-fix rounds through the build runner on the scratch patch stacked on its base in the user tree (same prepare / restore), cancel, startup recovery (running jobs failed, scratch dirs removed). Mutual exclusion with build and pre-scan jobs.
- API: rework plan for a selection (order, missing prerequisites, estimate, preselected rungs), start, job status, cancel, attempts per item, accept / reject with note (accept refused while a base is not accepted), rework summary counts; items API `rework_status`, filter; build and pre-scan job results list their rework candidates.
- Test: a chain where the prerequisite is reworked first and the dependent on top; a closed prerequisite left out; build-fix round that fixes a compile error; no-progress stop; per-job cap; accept blocked by a proposed base; ripple marks dependents stale; second rework starts from the failure; cancel cleans up.

**5.7 Rework UI**
- "Rework…" dialog (bulk toolbar and item Migration tab), job panel in `JobsPopup`, backlog column, count bar and filter, "Rework these?" in build and pre-scan job results. Migration tab: patches with review state and base chain, the original next to the proposed patch per file, findings, Copilot's explanation, attempt details (rungs, calls, rounds, build logs), Accept / Reject with note.
- Test: component tests for the dialog (missing prerequisites, preselected rung, caps), review actions, blocked accept, stale reason, the job-result offer.
